# 服务启动后的 HDA / DA 验证方法

适用本包 `presets/format_demo/`、程序 v1.5.2。目标是确认“历史正确、实时在播、追加正确”，不是长时间性能压测。本文全部时间均标为 **UTC**，不要把本地显示时间与UTC直接比较。

## 1. 启动与连接

1. 检查系统时间正常、端口没有占用。整包复制后双击包根目录 `start.cmd`；或在包根目录执行 `hda_mocker_4_v1.5.2.exe --config presets\format_demo\config.yaml`。
2. 等控制台出现 `phase=running` / `service running`。只有窗口打开、进程存在或端口可连接，不算通过。
3. 使用支持 OPC UA 当前值、订阅和原始历史读取的客户端连接。不同客户端界面不同，以下按功能描述，不绑定某个软件。

默认参数（修改过配置时以 `presets/format_demo/config.yaml` 为准）：

| 项目 | 内容 |
|---|---|
| Endpoint | `opc.tcp://127.0.0.1:14860` |
| 安全 / 用户 | 本例未配置证书或账户，使用 None / 匿名 |
| 节点目录 | `Objects/HDA_Mocker` |
| namespace URI | `urn:hda:mocker4:format-demo` |
| NodeId | `ns=3;s=sample_temperature`、`ns=3;s=sample_pressure`、`ns=3;s=sample_quality` |
| 简要诊断 | `http://127.0.0.1:14861/v1/diag` |

客户端若能按namespace URI解析索引，优先使用URI；本配置索引为3。跨机器时不能用127.0.0.1连接服务器，修改同一配置中的服务器实际主机地址、检查防火墙和端口。不要另维护一份地址注册表。

**通过条件：** 能找到3个基础位号，能读取完整DataValue（数值、质量、SourceTimestamp）。有些时刻 `sample_quality` 故意为Bad，仍要保留其值和时间，不要让客户端的“遇到Bad就抛错”模式挡住观察。

## 2. 验证预存 HDA：先查固定的9月窗口

对每个位号执行 **Raw / 原始历史查询**，不用插值、聚合、重采样或客户端补点：

```text
开始：2026-09-01T00:00:00Z
结束：2026-09-01T00:00:16Z
```

如果客户端采用北京时间显示，对应9月1日08:00:00～08:00:16；不要直接用本地00:00去查询。

协议参数必须注意：`IsReadModified=false`、`ReturnBounds=false`；正常查询和续读设 `ReleaseContinuationPoints=false`。有continuation point就继续读，不能只取第一页。若客户端没有这些设置且返回不支持，换支持原始HistoryRead参数的工具，不先判数据损坏。

以下时间均为 **2026-09-01 UTC**；`NULL` 是无数值，不是字符串。

### sample_temperature：应有6点，全部Good(0)

| 时间 | 值 |
|---|---:|
| 00:00:00.125 | 20 |
| 00:00:01.125 | 21 |
| 00:00:04.125 | 22 |
| 00:00:06.375 | 0 |
| 00:00:08.125 | -1 |
| 00:00:10.125 | 23 |

### sample_pressure：应有4点，全部Good(0)

| 时间 | 值 |
|---|---:|
| 00:00:00.125 | 100 |
| 00:00:02.625 | 101 |
| 00:00:06.375 | 102 |
| 00:00:10.125 | 103 |

### sample_quality：应有5点，不能过滤掉Bad

| 时间 | 值 | 完整UA质量码 | 含义 |
|---|---:|---:|---|
| 00:00:00.125 | 1 | 0 | Good |
| 00:00:02.625 | NULL | 2150694912 | BadNoCommunication |
| 00:00:04.125 | 2 | 0 | Good |
| 00:00:08.125 | 3 | 9830400 | GoodLocalOverride，仍属Good |
| 00:00:10.125 | 4 | 2150694912 | 带值BadNoCommunication |

**通过条件：** 6/4/5点，总计15点；数值和质量一致；`.125`、`.375`、`.625` 等毫秒未丢失；可显示为`.125000`，这是同一精度内容的补零。

文件末行00:00:15.025是全空行，不应产生额外历史点。temperature空格不能补成21/22等保持值；真正的0和-1必须存在。

客户端如能限制单页条数，可设每页2点，确认temperature至少3页、quality至少3页，最终仍为6/5点且无重复。若客户端自动续读，则核对总结果即可。

这里只查9月源窗口。服务启动后追加的实时点在运行当天，不应把它们混入“预存历史应为15点”的判断。

## 3. 验证 DA：观察至少60秒

订阅3个位号，或周期读取完整DataValue。建议订阅/采样目标间隔100ms，记录服务器实际修订的间隔；定期读只能看到部分状态，不能证明每个中间观测都收到。

至少记录：位号、Value、原始StatusCode、SourceTimestamp、客户端实际接收UTC时间。观察60秒，尽量覆盖多个15秒循环，不要刚收到一次初始通知就结束。

以某轮首行真实更新的SourceTimestamp为 **B**，应有下列行为。B是播放起点，不是源文件9月时间，也不是程序启动日志时间；首轮可能在客户端连接前已经开始。

| 相对B | 发生真实观测的位号 | 其他位号的行为 |
|---|---|---|
| 0秒 | temperature=20/Good，pressure=100/Good，quality=1/Good | — |
| 1秒 | temperature=21/Good | pressure保持100，quality保持1/Good |
| 2.5秒 | pressure=101/Good，quality=NULL/Bad | temperature保持21 |
| 4秒 | temperature=22/Good，quality=2/Good | pressure保持101 |
| 6.25秒 | temperature=0/Good，pressure=102/Good | quality保持2/Good |
| 8秒 | temperature=-1/Good，quality=3/GoodLocalOverride | pressure保持102 |
| 10秒 | temperature=23/Good，pressure=103/Good，quality=4/Bad | — |
| 14.9秒 | 无真实观测，不应生成新的值通知或历史点 | 保持23、103、4/Bad |
| 15秒 | 下一轮首行 | 回到20、100、1/Good |

保持时不应因为源格的status填0就自动清除上一次Bad；14.9秒全空行后，quality仍为4/Bad。
初始化会从上一轮末尾找值，可能短暂读到23、103、4/Bad；客户端首次订阅会给当前值通知，这不是证明正在播放的证据。

**通过条件：** 运行当天的SourceTimestamp持续推进，状态序列反复出现，而不是一直停在初始化值；真实0、负数、无值Bad、带值Bad和Good子码均能正确显示。

订阅实现会合并中间通知，缺少某条通知不直接等于HDA漏写。也不要仅凭“值相同”去重：不同轮的相同值仍是不同时间的观测。

## 4. 验证实时 HDA 追加与跨轮

运行60秒后，重新发起覆盖最近60秒的原始历史查询，而不是继续使用启动前建立的旧分页快照。

1. 从temperature最近历史中找到值20、随后按21/22/0/-1/23变化的一轮，取20那一点的时间为B。不要把客户端初始通知时间当B。
2. 选一轮已经完整播放结束的B。查询该轮 `[B, B+15秒)`；若工具只支持闭区间，结束取 `B+15秒-1微秒`，避免把下一轮首点算进来。
3. 检查该轮temperature/pressure/quality分别有6/4/5点，值和质量与第2节相同，时间改为 `B + 表中相对偏移`。
4. 相同位号下一轮首点应为B+15秒。例如temperature最后23在B+10秒，下一轮20在B+15秒，间隔5秒，而不是100ms；100ms只指全空末行B+14.9秒到下轮首行。
5. 每个位号最新DA观测，应能在对应实时HDA里找到相同SourceTimestamp、值、质量；保持值不应反复形成额外历史点。查不到时先重新查询、核对时间窗口和质量，再判断失败。

**通过条件：** 新点在运行当天持续追加；完整轮次每轮15个真实点，不把3个位号每100ms都补成历史；历史与当前值能够对应。计划时间、质量和数值不能错配。

## 5. 怎样看待100ms与性能

本示例能检查规则和大致节奏，不是正式压力测试。

- 100ms是到期检查周期，不保证客户端恰好每100ms收到通知。
- HDA里的SourceTimestamp是计划播放时间。它间隔准确，不等于数据库或网络每次都及时完成。
- 如要观察延迟，先同步服务器与客户端时钟，记录“接收UTC时间－SourceTimestamp”和请求耗时；时钟偏差、网络及客户端处理都可能影响结果。
- 多个应到期观测持续查不到、落后程度增长、播放冻结或日志报错，应判异常；不能仅凭诊断status=ok宣告性能通过。
- 若要定义延迟阈值、高并发、长时间订阅或24小时稳定性，应另定现场验收条件。本例没有给出未经实测的毫秒级SLA。

## 6. 常见问题与重启检查

| 现象 | 先检查 |
|---|---|
| 连接被拒绝 | 是否已到running、端口占用、当前config地址、防火墙、本机/远端地址是否混淆 |
| HDA报不支持 | 是否误用修改历史、ReturnBounds=true，或查询的是聚合历史 |
| HDA Good但0点 | UTC/本地时间、窗口、ReleaseContinuationPoints是否误为true、是否错误释放续读点 |
| quality显示Bad | 按时间线判断；本例两种Bad是故意的，不能一律当服务故障 |
| 只有一次当前值通知 | 排除初始通知后继续观察SourceTimestamp；检查日志和诊断，可能是冻结而非正常播放 |
| 全量历史点数多于15 | 是否把服务运行当天追加的历史也统计进来 |
| 时间只显示到秒 | 先打开毫秒/微秒显示或查看原始时间，区分显示省略与实际精度丢失 |
| 重启说输入文件改变 | Parquet哈希变了；备份旧runtime，用新runtime验收，不自动删除旧库 |
| 提示当前时间不晚于历史 | 检查系统UTC和源时区；不要擅自平移数据绕过保护 |

同一份数据不变、runtime保留时，重启应跳过重复导入，9月固定窗口仍是6/4/5点，不应翻倍。时间轴DA重启从源首行开始，用新的播放起点追加当前历史。

正式停止优先在服务控制台Ctrl+C并等待退出。不要在运行时复制DuckDB/WAL或删除runtime。若准备“全新首次导入”演示，先停服务，再把旧runtime完整移到备份位置，确认无需沿用后才用新目录启动；原Parquet保持不变。
